# COM230 · Semana 2 · Classes, objetos, encapsulamento e ocultação de informação

Explicações e exercícios autorais baseados nas fontes consultadas em 02/11/2026. A análise integral de livros, vídeos e lives permanece pendente; confira os status abaixo.

## Síntese

Encapsulamento reúne estado e operações e define um contrato de uso; ocultação limita a exposição de detalhes.

Construtores e métodos devem manter o objeto em estado válido.

Estado de instância e estado static têm associações diferentes; memória e recursos externos também exigem distinção.

## Objetivos

- Usar atributos, métodos, construtores e static.
- Controlar visibilidade e preservar invariantes.
- Distinguir encapsulamento de geração automática de acessadores.

## Contrato e invariantes

Uma classe oferece operações que mantêm suas regras. Se um saldo não pode ser negativo no modelo, expor o campo permite violar a regra. A operação deve validar antes de alterar estado.

private não basta: um setter sem critérios ou uma coleção interna mutável exposta pode romper a proteção. Pergunte o que o objeto permite fazer, em vez de gerar um setter para cada campo.

## Visibilidade e construção

public expõe o membro aos clientes com acesso ao tipo; private restringe acesso segundo as regras da classe envolvente. Sem modificador há acesso de pacote. protected permite acesso no pacote e por subclasses, com regras adicionais entre pacotes.

Construtor tem nome da classe e nenhum retorno declarado. this identifica o objeto atual. Ao declarar um construtor, não se recebe automaticamente outro sem argumentos. Use a menor visibilidade que atenda ao contrato.

## static, memória e recursos

Cada objeto possui seus campos de instância. Um membro static pertence à classe em seu contexto de carregamento. Usar static para um saldo que deveria variar por conta compartilha estado indevidamente.

Java não possui destrutor determinístico como C++. Coleta de lixo trata memória, sem garantir fechamento imediato de arquivos ou sockets. Recursos externos devem ser fechados explicitamente, preferencialmente por try-with-resources quando aplicável.

## Programa completo com regra protegida

Saldo em centavos simplifica a representação do exemplo. O construtor rejeita saldo inicial negativo e depositar exige valor positivo. A saída é 1500 e 1; não é uma implementação financeira completa.

Uma chamada depositar(-100) lança IllegalArgumentException antes de mudar o saldo. A regra fica no objeto, independente de menu ou interface gráfica.

```java
public class Main {
    static class Conta {
        private int saldo;
        private static int criadas;
        Conta(int inicial) {
            if (inicial < 0) throw new IllegalArgumentException("Saldo inicial");
            saldo = inicial; criadas++;
        }
        void depositar(int valor) {
            if (valor <= 0) throw new IllegalArgumentException("Valor positivo exigido");
            saldo += valor;
        }
        int getSaldo() { return saldo; }
        static int getCriadas() { return criadas; }
    }
    public static void main(String[] args) {
        Conta c = new Conta(1000);
        c.depositar(500);
        System.out.println(c.getSaldo());
        System.out.println(Conta.getCriadas());
    }
}
```

## Prática comentada

### 1. setIdade sem validação preserva uma idade válida só porque o campo é private?

1. Não. O método ainda pode aceitar valores inválidos.
2. Defina o contrato e valide antes de alterar estado.
3. Considere se o dado e sua mutação fazem sentido no domínio.

### 2. Duas contas têm 100 e 200 centavos. Deposite 50 na primeira.

1. Os saldos passam a 150 e 200.
2. O contador static de criadas vale 2.
3. Saldo static teria compartilhamento inadequado nesse modelo.

### 3. Como uma lista interna retornada pode expor implementação?

1. O cliente pode alterar a lista fora das operações da classe.
2. Isso pode violar invariantes.
3. Considere cópia defensiva ou visão não modificável, esclarecendo a profundidade da proteção.

## Erro comum

Getters e setters indiscriminados não garantem encapsulamento. Coleta de lixo não substitui fechamento de recursos.

## Flashcards

- **Construtor tem retorno?** Não; inicializa a instância e tem o nome da classe.
- **this?** Referência ao objeto atual em contexto de instância.
- **Campo static?** Membro da classe, compartilhado no contexto correspondente.
- **private garante sozinho invariantes?** Não; operações também precisam validar e respeitar regras.
- **Acesso sem modificador?** De pacote.
- **Java tem destrutor determinístico como C++?** Não; recursos externos devem ser fechados explicitamente.

## Questões autorais

### 1. static representa:

A. Um membro da classe, compartilhado no contexto correspondente.
B. Um campo independente obrigatório por objeto.
C. Uma constante obrigatoriamente.
D. Imutabilidade automática.

**Gabarito:** A. static não equivale a final; determina associação à classe.

### 2. Um construtor válido é:

A. Conta(int valor) { ... }
B. void Conta(int valor) { ... }
C. int Conta(int valor) { ... }
D. new Conta(int valor) { ... }

**Gabarito:** A. Construtores não têm tipo de retorno; void Conta seria método.

### 3. Qual protege melhor uma regra?

A. Validar antes de alterar estado privado.
B. Tornar o campo público.
C. Setter que aceita tudo.
D. Confiar só no menu.

**Gabarito:** A. O objeto deve manter seu contrato independentemente do cliente.

### 4. Sem modificador de acesso, um campo é:

A. De pacote.
B. Sempre public.
C. Sempre private.
D. Sempre protected.

**Gabarito:** A. A visibilidade padrão permite acesso no mesmo pacote.
