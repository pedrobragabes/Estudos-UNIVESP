# COM230 · Semana 7 · Streams, serialização, threads e redes

## Síntese

I/O transporta bytes ou caracteres; java.util.stream processa sequências de elementos.

Serialização representa estado em bytes, exigindo compatibilidade e cuidado com origem dos dados.

Threads compartilham recursos; sockets conectam processos, mas não definem o protocolo da aplicação.

## Objetivos

- Distinguir I/O e API Stream.
- Serializar objetos de origem controlada.
- Criar threads e reconhecer corridas e sincronização.
- Explicar sockets TCP, cliente–servidor e delimitação de mensagens.

## Bytes, caracteres e buffer

InputStream e OutputStream tratam bytes; Reader e Writer tratam caracteres. Converter texto exige charset, preferencialmente explícito. read retorna −1 no fim do fluxo; available não é teste geral de fim de arquivo nem de mensagem de rede.

Buffer agrupa operações pequenas sobre o recurso subjacente. flush envia dados pendentes do buffer sem necessariamente fechar o recurso. Delimite o tempo de uso com try-with-resources e diferencie fechar, descarregar buffer e detectar fim.

## API Stream e lambdas

filter seleciona elementos; map transforma valores; operações terminais como collect ou forEach consomem o pipeline. Operações intermediárias são em geral preguiçosas. Uma Stream não é a coleção fonte e não deve ser reutilizada após consumida.

Evite efeitos colaterais dependentes de ordem ou estado compartilhado. Processamento paralelo não garante aceleração nem resolve concorrência automaticamente. No exemplo, o resultado é [ANA, ALANA] e a coleção original permanece igual.

```java
import java.util.*;
import java.util.stream.Collectors;
public class Main {
    public static void main(String[] args) {
        List<String> nomes = Arrays.asList("Ana", "Bia", "Alana");
        List<String> resultado = nomes.stream()
            .filter(n -> n.startsWith("A"))
            .map(String::toUpperCase)
            .collect(Collectors.toList());
        System.out.println(resultado);
        System.out.println(nomes);
    }
}
```

## Serialização e desserialização

Serializable marca classes cujo estado pode ser serializado pelo mecanismo nativo. ObjectOutputStream escreve e ObjectInputStream lê; o grafo alcançável deve ser compatível. static não representa estado da instância; transient exclui um campo da serialização padrão.

serialVersionUID participa da identificação de versão. Serialização não criptografa segredos. Desserializar conteúdo não confiável pode ser perigoso: o exemplo só lê bytes que ele mesmo produziu, sem servir de protocolo para entrada arbitrária de rede. A saída é Revisar e null.

```java
import java.io.*;
public class Main {
    static class Nota implements Serializable {
        private static final long serialVersionUID = 1L;
        String texto;
        transient String temporario;
        Nota(String t) { texto = t; temporario = "rascunho"; }
    }
    public static void main(String[] args) throws IOException, ClassNotFoundException {
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(new Nota("Revisar"));
        }
        try (ObjectInputStream in = new ObjectInputStream(
                new ByteArrayInputStream(bytes.toByteArray()))) {
            Nota lida = (Nota) in.readObject();
            System.out.println(lida.texto);
            System.out.println(lida.temporario);
        }
    }
}
```

## Threads e estado compartilhado

Runnable representa a tarefa. Thread.start solicita execução em outra thread; chamar run diretamente é uma chamada normal na thread atual. join espera término; sleep não é estratégia confiável de coordenação.

contador++ envolve leitura, cálculo e escrita, sem atomicidade automática. synchronized protege a seção crítica quando todas as operações usam o mesmo monitor, com garantias relacionadas de visibilidade. volatile não torna incremento composto atômico. O programa espera as duas threads e imprime 2000.

```java
public class Main {
    static class Contador {
        private int valor;
        synchronized void incrementar() { valor++; }
        synchronized int get() { return valor; }
    }
    public static void main(String[] args) throws InterruptedException {
        Contador c = new Contador();
        Runnable tarefa = () -> { for (int i = 0; i < 1000; i++) c.incrementar(); };
        Thread a = new Thread(tarefa), b = new Thread(tarefa);
        a.start(); b.start();
        a.join(); b.join();
        System.out.println(c.get());
    }
}
```

## Sockets e protocolo

O servidor associa uma porta e aguarda conexão com accept. O cliente conecta a endereço e porta. Ambos recebem fluxos de entrada e saída. TCP oferece bytes ordenados, sem preservar fronteiras das escritas da aplicação.

Defina enquadramento por linhas, tamanho prefixado ou outra regra. Trate encerramento, timeout, dados inválidos e liberação de recursos. Atender vários clientes pode exigir threads ou outra estratégia concorrente; o estado compartilhado ainda precisa de coordenação.

A demonstração usa apenas loopback, porta temporária e uma troca por linha. Imprime Recebido: Ola. Ela ilustra o mecanismo, sem pretender ser servidor de produção.

```java
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;
public class Main {
    public static void main(String[] args) throws Exception {
        try (ServerSocket servidor = new ServerSocket(0, 1, InetAddress.getLoopbackAddress())) {
            Thread atendimento = new Thread(() -> {
                try (Socket s = servidor.accept()) {
                    s.setSoTimeout(3000);
                    BufferedReader in = new BufferedReader(new InputStreamReader(
                        s.getInputStream(), StandardCharsets.UTF_8));
                    PrintWriter out = new PrintWriter(new OutputStreamWriter(
                        s.getOutputStream(), StandardCharsets.UTF_8), true);
                    String pedido = in.readLine();
                    out.println("Recebido: " + pedido);
                } catch (IOException e) { throw new UncheckedIOException(e); }
            });
            atendimento.start();
            try (Socket cliente = new Socket(InetAddress.getLoopbackAddress(), servidor.getLocalPort())) {
                cliente.setSoTimeout(3000);
                BufferedReader in = new BufferedReader(new InputStreamReader(
                    cliente.getInputStream(), StandardCharsets.UTF_8));
                PrintWriter out = new PrintWriter(new OutputStreamWriter(
                    cliente.getOutputStream(), StandardCharsets.UTF_8), true);
                out.println("Ola");
                System.out.println(in.readLine());
            }
            atendimento.join();
        }
    }
}
```

## Estados de threads e tarefas gerenciadas

Os estados de Thread em Java incluem NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING e TERMINATED. RUNNABLE abrange execução e aptidão para executar conforme o escalonamento; não garante um núcleo exclusivo. BLOCKED indica espera por monitor. sleep não libera monitores já adquiridos; wait, chamado sob o monitor adequado, libera esse monitor durante a espera.

Runnable descreve uma tarefa; uma Thread fornece um caminho de execução. ExecutorService separa a submissão da tarefa da gestão dos trabalhadores. Após submeter, encerre o serviço de forma adequada e aguarde término quando o resultado exigir conclusão. shutdown não aguarda sozinho todas as tarefas; join aguarda uma Thread específica. Nenhuma dessas operações torna automaticamente atômico um incremento compartilhado.

volatile estabelece garantias de visibilidade e ordenação para leituras e escritas da variável; não torna contador++ atômico, pois essa expressão combina leitura, cálculo e escrita. Para uma atualização indivisível, use sincronização coerente ou uma classe atômica apropriada. Ao usar wait, teste a condição em um laço: pode haver despertar sem que a condição necessária esteja satisfeita.

## Padrões de projeto: a leitura de Sommerville

A seção 7.2 descreve padrões por nome, problema, estrutura da solução e consequências. Um padrão é uma organização recorrente de responsabilidades, adaptada ao contexto; não é um bloco de código a copiar sem examinar forças e custos. Essa leitura conecta o estudo de classes, interfaces e baixo acoplamento à organização do projeto.

No Observer, um objeto que mantém estado permite registrar observadores e os notifica quando o estado muda. Assim, diferentes apresentações podem reagir sem que o sujeito conheça cada classe concreta. Como exemplo autoral, um placar notifica um painel e um histórico. É preciso definir registro, remoção, conteúdo da notificação e tratamento de falhas. Observer não cria threads nem garante segurança de concorrência por si só.

## Prática comentada

### 1. Uma leitura TCP recebeu parte da mensagem. O transporte necessariamente falhou?

1. Não. TCP não preserva as fronteiras das escritas.
2. Leia até completar o tamanho esperado ou encontrar o delimitador definido.
3. Trate fim e timeout sem supor uma mensagem inteira por read.

### 2. Duas threads incrementam contador mil vezes cada sem proteção. O resultado é necessariamente 2000?

1. Não. Intercalações podem perder incrementos.
2. Use monitor compartilhado ou abstração atômica.
3. Espere término com join antes de observar o total.

### 3. Um transient String preenchido retorna com qual valor na desserialização padrão?

1. Não é gravado como parte do estado padrão.
2. Sem restauração personalizada, retorna ao padrão da referência: null.
3. Isso não significa criptografia nem segurança para entrada não confiável.

### 4. Compare filter, map e operação terminal.

1. filter seleciona e map transforma.
2. A terminal consome o pipeline.
3. Essas operações não alteram automaticamente a coleção fonte.

### 5. Um placar precisa atualizar painel e histórico a cada alteração. Como aplicar Observer e o que ainda precisa ser decidido?

1. Defina um contrato de observador e permita cadastrar e remover interessados no placar. Ao alterar o estado, o placar chama a operação de atualização de cada observador.
2. Faça painel e histórico implementarem o contrato; o placar depende da interface, evitando chamadas específicas a cada apresentação concreta.
3. Defina se a entrega será síncrona, como lidar com exceções e como sincronizar alterações concorrentes se houver. O padrão, isoladamente, não oferece essas garantias.

## Erro comum

I/O Stream e API Stream têm contratos diferentes. TCP não fornece mensagens prontas; volatile não torna contador++ atômico.

## Flashcards

- **Fim de InputStream.read()?** Retorno −1; available não é teste geral de fim.
- **Reader e InputStream?** Caracteres e bytes, respectivamente; a conversão requer charset.
- **filter e map?** Selecionar elementos versus transformar valores.
- **transient e static na serialização?** transient é excluído; static pertence à classe e não ao estado serializado da instância.
- **start e run?** start solicita outra thread; run direto é chamada normal.
- **TCP preserva mensagens?** Não. A aplicação define enquadramento por tamanho, linhas ou outra regra.
- **volatile torna incremento atômico?** Não; o incremento é uma operação composta.
- **join?** Espera o término de outra thread.

## Questões autorais

### 1. Qual transforma elementos da API Stream?

A. map.
B. filter exclusivamente.
C. flush.
D. accept.

**Gabarito:** A. map transforma; filter seleciona. flush e accept pertencem a outros contratos.

### 2. −1 de InputStream.read indica:

A. Fim do fluxo.
B. Um byte válido necessariamente.
C. Mensagem vazia de um caractere.
D. Que available deve ser usado para continuar indefinidamente.

**Gabarito:** A. read retorna byte como inteiro não negativo ou −1 no fim.

### 3. thread.run diretamente:

A. Executa como chamada normal na thread atual.
B. Equivale a start obrigatoriamente.
C. Cria outra JVM.
D. Equivale a join.

**Gabarito:** A. start solicita a execução concorrente; run sozinho é método comum.

### 4. Um protocolo TCP por linhas deve:

A. Definir delimitadores e tratar encerramento e timeout.
B. Supor um read por write.
C. Ignorar charset sempre.
D. Desserializar qualquer objeto remoto.

**Gabarito:** A. O fluxo de bytes precisa ser interpretado e delimitado pela aplicação.

### 5. Na serialização padrão:

A. transient não recupera automaticamente o valor original.
B. Todos os campos são criptografados.
C. static vira estado de cada instância.
D. Qualquer origem remota torna-se confiável.

**Gabarito:** A. O campo é excluído da representação padrão; compatibilidade e segurança exigem decisões adicionais.
