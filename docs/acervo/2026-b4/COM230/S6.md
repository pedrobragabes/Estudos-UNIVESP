# COM230 · Semana 6 · Tratamento de exceções

Explicações e exercícios autorais baseados nas fontes consultadas em 02/11/2026. A análise integral de livros, vídeos e lives permanece pendente; confira os status abaixo.

## Síntese

Uma exceção abandona o fluxo normal e procura um tratador compatível na pilha.

Exceções verificadas exigem captura ou declaração; o ramo RuntimeException é não verificado.

Tratar uma falha requer decisão coerente; capturas vazias escondem problemas.

## Objetivos

- Identificar propagação na pilha e capturas compatíveis.
- Distinguir checked, unchecked, throw e throws.
- Criar exceções e gerenciar recursos sem esconder falhas.

## Hierarquia e propagação

Throwable é a base de objetos lançáveis. Exception e Error são ramos diferentes; RuntimeException deriva de Exception. Exceções verificadas fora dos ramos não verificados precisam ser capturadas ou declaradas conforme as regras da linguagem.

Ao lançar uma exceção, o restante do trecho normal é abandonado. O runtime procura catch compatível no método ou nos chamadores. A pilha de chamadas ajuda a identificar a origem; declarar throws não executa recuperação.

## Capturar, declarar e lançar

try delimita operações e catch trata tipos compatíveis. Capturas específicas devem vir antes das gerais para evitar um tratador inalcançável. throw lança uma instância; throws declara possíveis tipos propagados na assinatura.

Uma exceção de domínio pode estender Exception para exigir decisão explícita de tratar ou propagar, ou RuntimeException conforme o contrato escolhido. Use mensagem útil e preserve a causa ao traduzir uma falha de outra camada, quando pertinente.

## finally e recursos

finally costuma executar na saída do try, com ou sem falha, mas não é garantia frente a encerramento abrupto da JVM. Retornar em finally pode ocultar retorno ou exceção anterior e deve ser evitado.

try-with-resources fecha recursos AutoCloseable e mantém informação sobre falhas suprimidas durante fechamento. Nem todo try precisa de catch: há try-finally e construções válidas de recursos. Capturar sem ação ou registro não resolve o problema.

## Programa completo: exceção de domínio

emprestar mantém a regra do objeto e lança uma exceção verificada quando não há disponibilidade. A primeira chamada imprime Emprestado; a segunda lança, e main imprime Sem unidades. Não ocorre um segundo empréstimo silencioso.

A mesma regra precisa funcionar independentemente do menu que usa o objeto. Se só a interface validasse, outro cliente poderia violar o contrato.

```java
public class Main {
    static class IndisponivelException extends Exception {
        private static final long serialVersionUID = 1L;
        IndisponivelException(String mensagem) { super(mensagem); }
    }
    static class Livro {
        private boolean disponivel = true;
        void emprestar() throws IndisponivelException {
            if (!disponivel) throw new IndisponivelException("Sem unidades");
            disponivel = false;
            System.out.println("Emprestado");
        }
    }
    public static void main(String[] args) {
        Livro livro = new Livro();
        try {
            livro.emprestar();
            livro.emprestar();
        } catch (IndisponivelException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

## Prática comentada

### 1. Trace try { int x=10/0; println(x); } catch(ArithmeticException e) { println("erro"); }.

1. A divisão inteira por zero lança ArithmeticException.
2. println(x) não é executado; o fluxo vai ao catch.
3. O tratador imprime erro e a execução pode continuar após a estrutura.

### 2. Uma operação lança IOException verificada. O chamador precisa decidir o quê?

1. Capturar e tratar, ou declarar throws IOException.
2. Escolher a camada com informação para recuperar ou comunicar a falha.
3. Propagar não é tratar: alguém ainda precisa decidir a resposta apropriada.

### 3. Por que catch(Exception e) {} é problemático?

1. Esconde a falha e pode sugerir sucesso ao cliente.
2. O estado pode ter sido parcialmente alterado.
3. Trate o caso específico e preserve informação de diagnóstico.

## Erro comum

throws não lança nem trata. finally não deve esconder a falha original.

## Flashcards

- **throw e throws?** throw lança instância; throws declara tipos propagáveis.
- **Obrigação checked?** Capturar ou declarar propagação conforme as regras do compilador.
- **RuntimeException é checked?** Não; seu ramo é não verificado.
- **Ordem de catch?** Mais específico antes do mais geral.
- **try exige catch sempre?** Não; há try-finally e try-with-resources válidos.
- **Por que preservar causa?** Para conservar o diagnóstico original ao traduzir a falha entre camadas.

## Questões autorais

### 1. throws informa:

A. Possíveis tipos propagados pelo método.
B. Que a falha foi tratada.
C. Que uma exceção foi obrigatoriamente lançada.
D. Que o método nunca falha.

**Gabarito:** A. A declaração é parte do contrato; throw lança uma instância.

### 2. Após falha no meio do try:

A. O restante do fluxo normal daquele try é abandonado.
B. A instrução seguinte sempre executa.
C. Todos os catches executam.
D. A exceção desaparece sem tratador.

**Gabarito:** A. Busca-se um tratador compatível no método ou na pilha.

### 3. Qual catch deve vir antes?

A. O mais específico.
B. Exception sempre antes das subclasses.
C. Throwable sempre antes de tudo.
D. A ordem nunca importa.

**Gabarito:** A. Um tratador geral anterior pode tornar o específico inalcançável.

### 4. try-with-resources:

A. Gerencia fechamento de AutoCloseable.
B. Elimina qualquer erro.
C. Substitui validação de domínio.
D. Cria objetos sem construtor.

**Gabarito:** A. A construção fecha recursos e lida com informação de falhas suprimidas.
